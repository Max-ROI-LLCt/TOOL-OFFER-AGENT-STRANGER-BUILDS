## Findings and disposition

1. **Fixed — natural-language readiness.** The direct command entered deterministic readiness assessment, but the conversational planner had no readiness action. Its generic reply could satisfy routing with only an introductory sentence; deliverable validation did not require a readiness assessment. Affirmative supported requests such as “Assess this offer’s readiness. Explain what is missing and whether its fictional-example restriction prevents commercial use.” now take the same deterministic assessment/card path before model interpretation. Negations, hypothetical questions and explicit field updates do not. Findings, evidence and fictional authorization restrictions are identical to the direct command, with no model call or state mutation. See `tests/test_live_findings.py` readiness tests.

2. **Fixed — retained intake review and correction.** `review intake` previously opened the replacement form; it never rendered current values. It now renders all nine retained fields, explicit missing values and saved-draft currency, plus a bounded review card with Correct a value and Cancel review. The correction action opens a distinct one-field form accompanied by retained values. The existing offer-card Correct a value action still opens that form directly. SDK review cards support a reject/cancel action; the installed form schema supports only a submit action, so form cancellation remains `cancel review`. Identical replacements preserve revision, draft currency, approval and source state; changed values invalidate only through the existing path. Bound, stale, replayed, cross-session and cancellation regressions remain enforced.

3. **Fixed — generated draft structure.** `render_draft` previously joined headings, fields and list items with single newlines, allowing native Markdown paragraphs to run together. It now uses separate heading blocks, seller fields, list entries, source attribution and boundary sections. Buyer explanation remains the concise path for large records. This changes presentation, not the stored draft, multipart encoding or cryptographic algorithms. Rendering assertions cover every section; actual corrected native layout has not been observed live.

4. **Fixed locally — current registry documentation.** Official publication is complete for `com.kinganlogic/tool-offer-agent` 1.4.9, active/latest at the supplied readback, published `2026-11-07T03:32:16.914361Z`, endpoint `https://tooloffer.kinganlogic.com/mcp`. `machine/registry-publication.json` records the owner-supplied evidence and original commit/release/server-file hash. Canonical guide, documentation and generated profile/discovery mirrors use that evidence. The complete registry-server bytes, not just displayed strings, match the publication metadata. The new candidate's actual runtime source is staged from the retained revision-85 source and current corrected modules; differing hashes are not represented as already deployed. Historical 1.4.7 publication/acceptance and 1.4.9 deployment receipts remain historical. Live Agentverse text is not changed by a local regeneration and requires a separately authorized update, not registry republication.

5. **Fixed — unsupported retention assurance.** Response guidance now explicitly prohibits blanket claims that secrets are not stored/retained/logged and distinguishes this agent from ASI and other platform retention. A generated-response guard removes the demonstrated assurance and instead says not to submit credentials without promising platform retention control. Existing secret-input rejection remains intact; a local persistence test is not a promise about every platform component.

6. **Fixed — partial multi-URL retrieval.** Parsing and retained `fields.docs` already supported one to three URLs, but fetching raised at the first failure: later URLs were not tried, and earlier successful local results were not committed. Fetching now attempts each valid URL and records each outcome, retains all successes, and reports each failed URL accurately. A failed refresh can preserve earlier text explicitly marked not refreshed. Incomplete drafting keeps successful requested sources. Comma-adjacent implicit URL input is normalized. Controlled one-to-three-URL cases cover all-success, first/last/all-failure, mixed refresh and partial drafting; an additional workflow fixture uses the real HTTP fetcher with injected DNS/HTTP responses and checks all actual GET targets, a 404 and retained body text. Private URLs, credential URLs, DNS pinning, redirect revalidation and maximum count remain enforced. Invented example-domain retrieval errors are not evidence of missing HTTP capability; fixture domains here are not contacted.

7. **Fixed for demonstrated assignment errors — access/payment/invocation.** Literal grounding checked that model-selected text occurred in the input, not that it belonged in the chosen field. Payment wording could therefore become invocation, and a combined access statement could be duplicated. Model guidance and assignment validation now distinguish permission/account access, payment and executable request instructions. Payment-only or ambiguous duplicate invocation is not saved; complete accepted access wording remains intact and the user gets one focused endpoint/tool/method/request clarification. The deterministic “Users can use it as MCP…” shortcut also no longer reclassifies a combined payment/access statement as invocation. Valid explicit HTTP/MCP requests and explicitly labeled seller corrections are preserved. This is not a claim of exhaustive semantic classification of arbitrary prose.

8. **Explained, with guidance fixed — revision and review.** State revision is a shared counter: a changed pricing correction advances 1→2; explicitly rebuilding a new draft advances 2→3. Draft v2 counts generated drafts separately; saved-draft revision 3 binds that draft to state revision 3. There was no demonstrated extra mutation to remove, and the existing lineage/hash calculations are unchanged. Readiness now checks the exact reviewed draft hash: current-draft review is already finished, whereas review of a superseded draft does not cover its rebuilt successor. Pending changes require rebuild before current-draft review. Labels explain these distinctions rather than resetting counters or carrying authorization forward.
