ANY AGENT FRAMEWORK

OAuth client credentials

  1. Create a P-256 signing key locally. Register only its public JWK at POST /oauth/register.
  2. Receive your stable client ID. Authenticate with private_key_jwt: sign a short-lived ES256 assertion and call POST /oauth/token.
  3. Use the one-hour Bearer token. Renew unattended with a fresh assertion; keys and quota identity stay the same.

Check your own registration using a fresh endpoint-bound assertion at POST /oauth/status. No client secret or refresh token.

EXISTING FETCH / UAGENTS IDENTITY

Sign. Enroll. Continue.

  1. Sign a fresh structured application using your existing Fetch identity. Include a separate RSA encryption public key and a hash of your private status capability.
  2. Submit to POST /api/access/applications. Receive a request ID and a credential encrypted only to you.
  3. Decrypt locally. Retrieve your status with the private AccessRequest capability; the public ID alone cannot access it.

Credentials expire in 30 days. Re-enroll with the same Fetch identity to retain your quota principal. Your private signing key never leaves your client.

A working client, not a contact form.

From this project’s checkout, with Node 22 or later and its dependencies installed, the client creates private key storage and handles assertions, renewal and encrypted delivery. Its output does not print credentials.

node machine/access-client.mjs register ~/.tooloffer/client.json "My agent"
node machine/access-client.mjs status ~/.tooloffer/client.json
node machine/access-client.mjs call ~/.tooloffer/client.json start_session '{"request_id":"<fresh UUID v4>"}'

Generate a fresh UUID for each new operation; the placeholder is not executable. For an existing Fetch key instead:

node machine/access-client.mjs fetch-enroll ~/.tooloffer/fetch.json /private/path/to/fetch-key

The Fetch key file must be mode 0600 and contain your existing 64-character hex signing key. Keep the identity state for recovery; never upload either file to this site or source control.

Implement OAuth in your own client

Read authorization-server metadata and MCP protected-resource metadata. Exact request schemas are in OpenAPI.

Token requests are form-encoded: grant_type=client_credentials, scope=tool_offer:machine, resource=https://tooloffer.kinganlogic.com/mcp, client ID, assertion type and signed assertion. JWT claims require iss=sub=client_id, exact endpoint aud, iat, exp within 120 seconds, and a fresh jti. Replays are rejected.

Client ID Metadata Documents, remote JWKS fetch, interactive authorization-code consent, enterprise federation and A2A task operations are not implemented. No interoperability claim beyond these supported routes.

KEEP THE RESULT, NOT JUST THE ACKNOWLEDGEMENT

A recoverable offer workflow.

  1. Start. Call start_session; retain its session ID.
  2. Supply. Send your source and commercial facts with send_message; retain its job ID.
  3. Retrieve. Poll get_result until complete. Pending, uncertain or truncated output is not a completed answer.
  4. Review. Call assess_offer_readiness, then export_offer. For multipart delivery, fetch every indexed part and verify each hash, total byte length and aggregate hash.

After an interrupted request, replay its same request ID and arguments. Do not create duplicate jobs with new IDs. See the complete multipart integrity fixture and recovery instructions.

Bounded by design.

Only scoped Bearer credentials can call protected operations. Cookies, registration IDs and browser WebMCP discovery do not grant access.

Enrollment: 5 requests/IP/UTC day; 100 globally. Access traffic: 30/IP/minute, 600 globally/minute, 10,000 globally/day. Credential issuance: 1,000 globally/day. Invalid attempts count. Honor Retry-After.

At most four issued tokens per identity remain valid at once. Rotation never resets machine quotas. Operators can revoke abusive identities; chat cannot mint credentials or grant operator privileges.

Native chat stays separate.

ASI:One uses the native Fetch Chat Protocol, not this restricted machine adapter. Native conversations and this adapter’s sessions do not share state; native chat is outside these adapter quotas.

No wallet connection, payment, publishing or FAHCE evaluation through machine calls. The existing separate human-approved evaluation checkout remains available in native chat, subject to readiness. A seller’s API price and an optional evaluation charge are different things.

Capabilities

  • Read public API/MCP documentation and retain source-attributed evidence.
  • Collect seller-stated customer, pricing, payment, access and invocation terms.
  • Draft, review and revise an offer within an isolated conversation.
  • Explain the buyer offer and prepare listing guidance without publication.
  • Assess retained offer readiness deterministically without inference or payment.
  • Export structured and human-readable records, with verified multipart retrieval when needed.

Boundaries

  • Does not certify sellers, prove service execution, grant resale rights or publish listings.
  • Does not share ASI:One conversation history with machine sessions.
  • Does not connect wallets, create checkouts, execute FAHCE or make payments through MCP/REST.
  • Does not sign, spend automatically or authorize a purchase on a buyer's behalf.
