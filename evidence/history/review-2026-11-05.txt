4. PAYMENT BRIDGE — CENTRAL TECHNICAL CONTRIBUTION

README.md leads with the bridge's problem and implemented mechanism.
docs/BRIDGE.md contains the architecture sequence and source/test map.

The Tool Offer contribution is the binding and recovery across the ASI workflow,
exact draft/request bytes, durable checkout, external buyer authorization,
validated x402 attempt and subsequent result retrieval. It includes the actual
outer-checkout Worker, payment relay, wallet UI, policy/receipt verification and
reconciliation code, plus the inner commercial custody Worker and Python client.

Actual order:
  Free ASI intake/drafting/review/readiness
  -> optional, restriction-gated evaluation request
  -> exact-request/draft-bound durable checkout creation or recovery
  -> free input compatibility screening (checkout may be input_blocked)
  -> external buyer connection and separate policy consent
  -> fresh screening and unsigned 402 challenge
  -> pinned payment-policy checks and persisted authorization stage
  -> buyer wallet signature
  -> retained signed payload, request/policy/signature validation
  -> persisted submitting stage, then one signed delivery attempt via relay
  -> separately retained response metadata, service result and proof outcome
  -> same-checkout status retrieval back through the ASI conversation.

Checkout creation, wallet connection and Finish review are NOT payment approval.
Current draft status alone is not payment eligibility. Explicit demonstrations
remain restricted. The free demonstration instructions never call check.

Duplicate preparation recovers a bound checkout. Signed-delivery uncertainty
locks another automatic payment attempt. Narrow retained-authorization retry and
expired/non-billable reconciliation paths have explicit predicates; expiry
reconciliation requires two independent finalized unused-nonce observations and
atomic preservation of the original attempt. No global exactly-once settlement
guarantee is claimed. Owner tokens, checkout capabilities and retained signed
material require protected custody; wallet private keys remain in the wallet.

Fetch/ASI provides chat/planner surfaces, ACP transport, cards, hosted execution
and discovery. FAHCE provides the external Diagnose computation and published
service/payment/attestation contracts. Wallet SDKs, x402 libraries/gateway and
Base/USDC provide the underlying signing/payment infrastructure. The package
does not claim native Fetch Payment Protocol, first-of-kind status, patentability,
independent novelty proof, seller certification or authority over buyer funds.

Current source map:
  tool_offer_agent/fahce_checkout.py and workflow.py
  bridge/checkout/checkout-worker.mjs
  bridge/checkout/browser.mjs and payment-policy.mjs
  bridge/checkout/expired-authorization.mjs
  bridge/checkout/attestation-verifier.mjs
  bridge/custody/transaction_custody.mjs
  tool_offer_agent/cloudflare_custody.py and commerce.py

The outer wallet-approval implementation is authoritative for current checkout.
The similarly named older inner adapter is excluded. Included server.mjs is a
historical local helper with regression tests, explicitly not the hosted backend.
Agent commercial custody and checkout wallet-state custody are distinct stores.
